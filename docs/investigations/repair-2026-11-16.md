## Cause 1: the hidden OBS recorder hangs on a crash prompt (fixed)

Observed with `-CheckOnly` and the launcher's own logs:

- `-CheckOnly` printed "Battle View prerequisites found" and exited 0.
- A portable `obs64.exe` (PID 23736) had been running since 2026-11-14 17:21:40, the
  same second as the last `logs/dashboard-backend.log` write. Nothing listened on
  port 4457.
- Its OBS log, `%LOCALAPPDATA%\Alpha4Gate\obs-portable\config\obs-studio\logs\2026-11-14 17-21-41.txt`,
  is one line long: `Crash or unclean shutdown detected`. The 2026-10-30 and 2026-11-06
  logs are the same single line. No plugin, so no websocket, ever loaded.
- The process owned a hidden top-level window titled **OBS Studio Crash Detected**.
- `obs-studio\.sentinel\` held four `run_*` files: 2026-10-14 13:13 (the launcher's
  OBS that was ended uncleanly the next morning) and one for each hung launch since.
- The last working session, 2026-10-15 07:53, had been started by hand with `--multi`.
  Its log shows no crash check, and at exit: `No crash sentinel location set for
  crash handler`.

Chain: the launcher starts OBS 32.2.2 with `-WindowStyle Hidden`. After any unclean
OBS exit, OBS asks about the crash in a dialog nobody can see. `--disable-shutdown-check`
does not suppress that dialog in this OBS version. The websocket never opens. After
30 seconds the launcher throws "isolated OBS recorder is unavailable on port 4457".
On the next launch it found the hung `obs64` already running, did not start another,
and failed the same way. Every Observer Rush launch from 2026-10-30 on failed this way,
before SC2 started.

Fix, in `scripts/launch-jev-battle.ps1`:

1. Start the isolated recorder with `--multi`, the setting proven on 2026-10-15. It
   disables the crash sentinel and the already-running prompt.
2. Recognise only the isolated recorder (by its exact `obs64.exe` path), never the
   operator's own OBS. Previously any `obs64` process, including the operator's own
   OBS, stopped the launcher from starting the isolated one.
3. If the isolated recorder has been up for 60 seconds or more without answering on
   port 4457, stop that one process and start a fresh one. It is hidden, so the
   operator cannot answer its prompt. A recorder younger than 60 seconds is waited on,
   not stopped.
4. `-CheckOnly` now names a stuck recorder ("A launch will restart it") and checks for
   Microsoft Edge.
5. New `-DecisionProvider typesafe|scripted`, default `typesafe` (unchanged for both
   shortcuts and `scripts/measure_jev_speed.py`). `scripted` never reads the key and
   spends no paid requests. It is the free way to test the whole chain.

## Cause 2: SC2 build 98310 and the uncommitted compatibility shim (reported)

SC2 is on `Base98310`. Only `bots/v13/bot.py` and `src/jev/bot.py` call
`orchestrator.sc2_compat.install()`. Both changes are uncommitted, and
`src/orchestrator/sc2_compat.py` is untracked. Observer Rush and `launch-jev.ps1` run
`src/jev/bot.py`, so they are covered in this working tree but not on any committed
branch. `bots/v0`-`v12` do not install the shim. The CLAUDE.md command
`python -m bots.v0 --role solo` and any evolve run with a pre-v13 opponent or parent
are exposed to the about-45-game-second crash (memory
`project_sc2_build_98310_ability_shift`; not reproduced here). Owners: `sc2_compat`
belongs to scoreboard; landing it and the bot-tree call sites is main's decision (ES.1).

## Paid acceptance run (operator-approved), and a second, intermittent fault

The operator approved one hosted run:
`powershell -NoProfile -File scripts/launch-jev-battle.ps1 -Difficulty 1 -MaxGameSeconds 90 -MaxWallSeconds 360`.

- Run `5778e27a7382434b885b77d3315b9346`. Key hand-off, dashboard, recorder and the
  game child all started. The host failed at the second browser measurement
  (`scripts/probes/jev_battle_view.py:563`, right after SC2 is restyled into the pane):
  `RuntimeError: Browser content geometry invalid: client=(0, 0, 146, 21), viewport={'w': 2146, 'h': 1163}`.
  The first measurement (line 506) had passed. The game child stopped cleanly at
  7.3 game-seconds (`status='stopped'`, exit 130). **No paid request was sent**: every
  strategy fact records `"calls": 0`.
- A free scripted repro with the same settings, run `f60b9220637f44ad900db8c075ff537c`,
  passed: battle ready, 90 game-seconds, 20 commands accepted, 0 rejected.

So far: 3 of 3 scripted runs pass and 1 of 1 hosted run failed at this step. The
step does not depend on the provider. 146x21 is the client area of a minimised
window, so the Edge child, or what `browser_hwnd` points at, was probably
minimised or replaced at that moment. Unproven. No earlier record of this failure
exists. Not fixed; a guess at the cause would not be proof.

The operator chose both follow-ups.

**Hardening** (`scripts/probes/jev_battle_view.py`, `wait_browser_origin`): during the
retries, an iconic Edge child is restored (`ShowWindow(SW_RESTORE)`). If the final
attempt still fails, the error now carries Edge's iconic flag, parent, parent-iconic
flag and window rect, so a recurrence names its own cause. The `BrowserWindows` fake in
`tests/test_jev_battle_launcher.py` gained `IsIconic`, `ShowWindow`, `GetParent` and
`GetWindowRect`, and two tests were added: a minimised child is restored and measured,
and the final error reports the window state. Checks: 84 passed, 6 skipped (both
focused files); ruff clean; `mypy --strict` on the probe shows the same 6 errors as the
committed file (none new; `scripts/` is outside the project's `mypy src bots` gate).
Red-on-garbage anchor: the new restore test fails against the committed probe
(`Browser content geometry invalid: client=(0, 0, 146, 21)`).

**Second paid run**, same command, run `1ae0cc5e422c48c0ac20d1cb443d26d4`: passed.
The battle was ready, it ran 90 game-seconds with 20 commands accepted and 0 rejected,
then `game_timeout` as requested, and the launcher exited 0. It did not exercise a
hosted request: `"calls": 0` throughout, and every slot `local_fallback`. That is by
design. Until the four-Gateway opening resolves, the hosted questions offer no options
(`"options": []`, reason `awaiting_first_answer`), and v2 asks only when more than one
option exists (`src/jev/strategy.py:1492`). Earlier v2 runs made their first call at
3.2 game-seconds (`749c6893`) and at 146 (`fd6182a0`, 35 calls in all). A 90-second cap
can therefore end before the first request.

What the two paid runs prove: the saved key reaches the game child without error, and
the whole Observer Rush chain starts and stops cleanly in hosted mode. The geometry
fault did not recur in 1 more hosted and 1 more scripted run, which fits an
intermittent cause.
