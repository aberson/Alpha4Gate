# Independent safety design challenge

Reviewer: fresh no-history sibling `/root/safety_design_challenge`. Read-only; no source edits, tests, games or network. Verdict: **NEEDS_DESIGN**. This advisory does not accept Step232 or authorize implementation.

The two-part direction is justified, but the document is not yet concrete enough to authorize implementation. The order repair is necessary; a bounded graph-derived resolution is credible. Neither requires a general simulator or command-authority subsystem.

References are to preserved 00bc515 unless prefixed docs/. Reviewer verified HEAD and read relevant complete function bodies.

1. The shared defect is real, but acknowledgement and completion need distinct contracts. Point-intent satisfaction ignores orders (operations.py:2522); acknowledgement accepts proximity (:3465); progress completes from proximity and clearance (:3502). The evidence records eight acknowledged/succeeded recovery tasks while all eight actors retain ATTACK orders and no replacement command occurs. Share an order-compatibility classifier, not necessarily one boolean across all three stages: compatible movement can acknowledge before arrival; completion still requires arrival and attack-move target clearance. Define compatibility for the entire queue, including matching first MOVE followed by ATTACK or movement away, target tolerance, and unknown abilities. The initial design states the requirement without specifying that contract.

2. Preventing false completion does not itself restore control. Once a task is running, _update_tasks calls progress without rechecking acknowledgement (runtime.py:2074). A stricter progress predicate could leave conflicting recovery work running until the no-progress deadline (:2117); _run_action sees the existing intent and skips reconciliation (:2345). Issued tasks instead wait for acknowledgement timeout and retry (:2053). Specify immediate handling of incompatible orders for issued/running recovery: retain/reissue, replace, or explicitly block, with bounded attempts and no duplicate dispatch. Otherwise false success becomes delayed ineffective recovery.

3. The invariant must include outstanding command authority. Safe observed orders are insufficient if an incompatible task still owns the actor and can retry. Satisfaction precedes refusal/preemption (runtime.py:2350 versus :2355,:2397); _assign_if_free leaves another holder in charge (:2450). Distinguish observed completion, authorized continuation, replacement awaiting observation, and blocked/refused transition. Issuing/accepting replacement never means completed recovery (:1579). Define compatible observed state with incompatible pending holder, including cross-lane ownership.

4. Removing the mirror addresses demonstrated drift, but execution boundary is unspecified. Mirror prefers assigned attackers (operations.py:779), authored selector tries free wave first (policy.json:3829). Existing _army_mode_is calls the mirror (operations.py:1734). Define preference-guard recursion avoidance, resolution lifetime, refresh after delayed answer, commit validation after earlier lanes change ownership/budgets. Traversal rolls back bindings/decision contexts, not arbitrary effects (runtime.py:2225); launch latch mutates immediately (:2331). Reuse the interpreter is a sound constraint, not yet an implementation boundary.

5. Retry priority and partial outcomes need explicit ordering. Retries precede graph evaluation (runtime.py:1470), reserve actor (:2164), then trigger refusal (:2435). Reserve release depends on mirrored emergency actors (:1442). Define retry suppression, reserve transfer and preservation of unaffected tasks. Mixed groups return running when some actors are active but others blocked (:2408); inspect every selected actor and distinguish partial progress from complete recovery.

Smallest next action: one short addendum, not another implementation round: order-state truth table, per-task reconciliation transitions, and resolve -> validate ownership/budget -> suppress conflicting retries -> commit/dispatch -> observe pseudocode. Name supported army operations and exact launch-latch commit point. Compare narrow extraction of existing army traversal/action planning with read-only mode. Extending eligibility mirror preserves duplication; general dry-run runtime exceeds scope.
