Four Gateways.
One inspectable player.

Jev v1 plays a complete Zealot rush using a decision graph. Watch what it chooses, what it is waiting for, and whether its actions actually succeed.

Planning complete; implementation and live acceptance have not started. The build plan is the source of truth.

What I heard

LLMs can build and revise the player between games. During a match, Jev itself evaluates game facts and executes its graph, without live LLM calls or an RL policy.

Start basic: one Protoss base, four Gateways, first attack at four Zealots, then continuous reinforcements. Jev owns every gameplay decision. First prove the player and dashboard work; connect evolution afterward.

Why this shape

SC2 facts→Executable graph→Explicit commands→Observed results

Economy, construction, production and army branches each get execution time. Waiting for minerals cannot freeze combat. Commands retain their originating node ID; the dashboard shows the same archived graph the match used.

Existing scripted gameplay routines will not secretly run Jev. Shared operations answer factual questions and carry out explicit commands.

Implementation defaults

These are agent-selected choices, not additional requirements attributed to you.

D1 Separate package

What: bots/jev/v1 with display name v1.jev; retain existing legacy IDs.

Why: Prove the player before broad version-registry migration.

Tweak: Timing and scope of family naming integration.

D2 Bounded behavior graph

What: JSON hierarchy with explicit operations, task state and nonblocking roots.

Why: Inspectable execution with structural validation and finite per-tick work.

Tweak: Node grammar, decision cadence and execution limits.

D3 Simple gameplay

What: 16 probes, no gas or upgrades, basic defense and search.

Why: Small complete strategy that leaves failure explanations understandable.

Tweak: Worker target, build priorities and defense distance.

D4 Confirm results

What: Observe action outcomes, limit retries and replan stalled tasks.

Why: Sending a build command is not proof that construction started.

Tweak: Retry count, deadlines and cooldowns.

D5 Read-only dashboard

What: Archived policy, bounded trace, atomic state snapshots and SVG graph inspection.

Why: Reuse the dashboard without coupling game execution to the browser.

Tweak: Trace retention and inspection presentation.

D6 Functional acceptance

What: Simple64 versus easy Terran, real smoke then three matches. Wins recorded, not required.

Why: Establish correct gameplay and useful evidence before tuning strength.

Tweak: Opponent, map, match limits and benchmark requirements.

Not in v1

Automated evolution or promotion; cross-family ladder matches; expansion or advanced units; graph editing in the browser; live LLM advice; graph embedded in the themed game window. The latter remains an explicit enhancement.

Risks to test

  • A valid graph can still make poor strategic choices. Progress checks and match limits expose this; they cannot prove winning behavior.
  • SC2 command timing and placement can fail. Tasks must confirm outcomes and recover from lost actors or rejected commands.
  • The dashboard backend follows the current bot version. Its Jev route mount must survive future pointer migrations.
  • SC2 must actually run for acceptance. Unit tests and fixture screenshots cannot replace the live smoke and complete matches.
